# Managed Process Supervisor Design

**Status:** Approved for implementation
**Date:** 2026-09-08
**Branch:** `feat/process-supervisor`
**Base:** `feat/local-authority-cli`

## 1. Goal

Add first-class long-lived process management to `chatgpt-system` so an authorized ChatGPT session can start a development server or similar bounded local process, inspect its status and logs, and stop it without routing through one-shot `terminal_run` calls or exposing arbitrary operating-system PID management.

The public MCP surface added by this phase is:

- `process_start`
- `process_list`
- `process_status`
- `process_logs`
- `process_stop`

`terminal_run` remains the primitive for bounded one-shot commands.

## 2. Scope

This phase covers process lifecycle only. It does not add:

- GUI automation, screenshots, mouse, keyboard, or active-window tools;
- `open_app` or `open_url`;
- browser/CDP/Playwright automation;
- arbitrary PID attach, inspect, signal, or kill;
- shell execution;
- interactive stdin/PTY sessions;
- root execution, `sudo`, privilege escalation, or a privileged helper;
- process persistence across an MCP server restart.

Those capabilities remain separate subsystems with separate designs.

## 3. Existing constraints that remain unchanged

1. User and Project authority do not have terminal capability.
2. Admin authority is terminal-capable but still runs as the current macOS user, not root.
3. Executables are basenames from the configured allowlist. Executable paths remain rejected.
4. `shell` is always `false`.
5. Child environments are sanitized. Secrets are not copied wholesale from the daemon environment.
6. Working directories must resolve inside the active authority scope and retain existing symlink-escape protections.
7. Command arguments may not contain NUL bytes.
8. Arguments, log contents, environment values, and opaque process IDs are not written to audit metadata.
9. The subsystem is not an OS sandbox and must not be described as one.

## 4. Architecture

### 4.1 Separation of responsibilities

The existing `ProcessService` keeps its current responsibility: execute one allowlisted command, collect bounded output, enforce timeout, and return a final result.

A new singleton `ProcessSupervisor` owns long-lived child processes for the lifetime of one `RuntimeServices` instance. It is the only component that stores child handles, opaque managed-process IDs, process-group information, lifecycle state, and bounded log buffers.

A small authority-scoped facade, created by `createScopedRuntime`, applies the current lease's `PathPolicy` and terminal command allowlist before delegating to the shared supervisor. This preserves one shared registry while keeping authorization checks specific to every MCP call.

The supervisor must never create a second `AuthorityManager` or a shadow runtime.

### 4.2 Runtime ownership

`RuntimeServices` gains one shared process supervisor. HTTP, stdio, the local authority control server, and all authority-scoped MCP calls continue to share the same runtime object.

Clean CLI shutdown calls the supervisor's `close()` method before process exit. `close()` attempts to terminate every still-running managed process group and waits for their close events within a bounded shutdown interval.

An abrupt daemon crash may leave a detached child process alive. Phase 1 does not attempt unsafe startup sweeping or PID-file recovery because the daemon cannot prove ownership of arbitrary surviving PIDs after restart. This limitation must be documented rather than hidden.

## 5. Process identity and registry

### 5.1 Opaque IDs

A managed process receives a cryptographically random opaque ID generated by the daemon. MCP never accepts an operating-system PID as a process identifier.

The OS PID/process-group ID is private implementation state. It is not returned by `process_start`, `process_list`, `process_status`, or `process_logs`.

### 5.2 Registry bounds

The runtime maintains at most `maxManagedProcesses` records. The default is **32**.

Running records are never evicted to make space. Completed records may be evicted oldest-first when the registry is full. If all records are running and the limit is reached, `process_start` fails with `LIMIT_EXCEEDED`.

Completed records are retained in memory only, so status and logs remain inspectable until eviction or daemon shutdown.

## 6. Authorization model

### 6.1 Start

`process_start` requires an active lease whose scoped runtime has terminal capability. Under the current profile model this means Admin authority only.

Before spawn, the scoped facade validates:

- terminal capability is enabled;
- `command` is a basename and exists in the lease command allowlist;
- no argument contains NUL;
- `cwd` resolves inside the current lease roots.

The resolved canonical working directory and command basename become immutable process metadata.

### 6.2 Later access

`process_list`, `process_status`, `process_logs`, and `process_stop` require an active lease. A process is manageable by that lease only when:

- the lease has terminal capability;
- the process command remains in the lease's command allowlist; and
- the process canonical working directory is inside the lease's current roots.

This intentionally binds management to authority scope rather than to the exact lease token. A new Admin lease can therefore recover and stop a process started by an older expired/revoked Admin lease, while a future narrower terminal-capable scope would only see processes whose cwd and command it is authorized to manage.

`process_list` filters out records the current lease cannot manage. Direct lookup of an unknown or unauthorized process ID returns the same `PROCESS_NOT_FOUND` error to avoid turning the registry into a scope-enumeration oracle.

Revoking an authority lease does **not** automatically terminate processes it previously started. Lease lifetime and process lifetime are separate. A newly approved compatible Admin lease can manage the process later.

## 7. Spawn model

Managed children use Node `spawn` with:

- `shell: false`;
- sanitized environment identical in policy to `terminal_run`;
- stdin ignored;
- stdout/stderr piped;
- a canonical authorized cwd;
- a separate process group on supported POSIX hosts.

`process_start` waits until the child has emitted `spawn` before returning success. An asynchronous spawn error fails the call and does not leave a registry entry. A child may exit immediately after the `spawn` event, so the returned summary reflects the record's current state at response time rather than promising that it is still `running`.

The current product target is macOS, with Linux CI support. Process-group signaling is used on POSIX. A non-POSIX fallback may signal only the direct child, but it must not invent arbitrary descendant discovery.

## 8. Lifecycle states

Externally visible states are:

- `running`
- `exited`
- `stopped`

A child that exits naturally becomes `exited`.

A child whose termination was initiated by `process_stop` or supervisor shutdown becomes `stopped` when its close event arrives.

A process that fails before successful spawn is not registered and therefore has no external state.

Every record stores:

- opaque `processId`;
- command basename;
- argument count, not argument values, for summary output;
- canonical cwd;
- state;
- ISO `startedAt`;
- optional ISO `exitedAt`;
- optional `exitCode`;
- optional signal name;
- stdout/stderr bounded buffers and truncation flags.

## 9. Logs

Each stream has its own bounded tail buffer. The default `maxProcessLogBytesPerStream` is **131072 bytes (128 KiB)**.

When a stream exceeds the limit, the oldest bytes are discarded and the buffer records `truncated: true`. This is tail semantics, which is more useful for development servers than retaining startup output forever.

`process_logs` returns only the currently retained stdout/stderr tails plus byte/truncation metadata. Its `bytes` field is the number of bytes currently retained in that stream's tail buffer, not the lifetime total emitted by the child. It never reads arbitrary files from disk and never creates log files automatically.

UTF-8 decoding uses replacement semantics for incomplete/malformed byte sequences. Log size is measured in bytes, not characters.

## 10. Stop semantics

`process_stop` is idempotent for a known manageable record.

For a running POSIX process group:

1. send `SIGTERM` to the managed process group;
2. wait up to `processStopGraceMs`, default **3000 ms**;
3. if still running, send `SIGKILL` to the same managed process group;
4. await the close event and return the final process status.

If the record is already `exited` or `stopped`, return its current status without signaling anything.

The supervisor never accepts a raw PID, negative PID, process-group ID, or signal name from MCP input.

## 11. MCP contracts

### 11.1 `process_start`

Input:

```ts
{
  authorityLeaseId: string;
  command: string;
  args?: string[]; // default []
  cwd?: string;    // default "."
}
```

Output is one `ProcessSummary` representing the process state at response time. Normally the state is `running`, but an immediately exiting child may already be `exited`.

No OS PID is returned.

### 11.2 `process_list`

Input:

```ts
{ authorityLeaseId: string }
```

Output:

```ts
{ processes: ProcessSummary[] }
```

Only manageable records are included, sorted newest-started first.

### 11.3 `process_status`

Input:

```ts
{ authorityLeaseId: string; processId: string }
```

Output is one `ProcessSummary`.

### 11.4 `process_logs`

Input:

```ts
{ authorityLeaseId: string; processId: string }
```

Output:

```ts
{
  processId: string;
  stdout: { content: string; bytes: number; truncated: boolean };
  stderr: { content: string; bytes: number; truncated: boolean };
}
```

### 11.5 `process_stop`

Input:

```ts
{ authorityLeaseId: string; processId: string }
```

Output is the final/current `ProcessSummary`.

## 12. Process summary schema

```ts
type ProcessSummary = {
  processId: string;
  command: string;
  argCount: number;
  cwd: string;
  state: "running" | "exited" | "stopped";
  startedAt: string;
  exitedAt?: string;
  exitCode?: number | null;
  signal?: string | null;
};
```

Argument values are deliberately omitted from list/status output. They remain only inside the private child invocation context and are not persisted in the managed-process record.

## 13. Configuration

`AppConfig.limits` gains:

- `maxManagedProcesses`, default `32`;
- `maxProcessLogBytesPerStream`, default `131072`;
- `processStopGraceMs`, default `3000`.

Environment overrides:

- `CHATGPT_SYSTEM_MAX_MANAGED_PROCESSES`
- `CHATGPT_SYSTEM_MAX_PROCESS_LOG_BYTES_PER_STREAM`
- `CHATGPT_SYSTEM_PROCESS_STOP_GRACE_MS`

All are positive integers.

`system_capabilities` reports the new limits. No separate enable flag is added. The existing terminal capability gate is the enablement boundary for process execution.

## 14. Shared execution policy

The one-shot `ProcessService` and new managed-process path must share executable validation and sanitized-environment construction so their security rules cannot drift.

A focused internal module should own:

- basename/allowlist validation;
- NUL argument rejection;
- sanitized child environment.

This is a targeted extraction, not a broader refactor of filesystem/Git policy.

## 15. Audit

Audit events:

- `process.start`
- `process.stop`
- existing `process.run` remains unchanged.

Audit metadata may include:

- command basename;
- argument count;
- terminal state transition where useful.

Audit metadata must not include:

- process ID;
- OS PID/process-group ID;
- argument values;
- environment values;
- stdout/stderr contents;
- authority lease IDs.

Read-only `process_list`, `process_status`, and `process_logs` do not require per-call audit events in Phase 1 because they expose only already-authorized in-memory state. This can be revisited if operational auditing needs change.

## 16. Errors

New stable error:

- `PROCESS_NOT_FOUND`: the supplied process ID is unknown or is not manageable by the current authority scope.

Existing errors remain:

- `POLICY_DENIED` for disabled terminal, command allowlist failures, invalid executable paths, invalid arguments, or cwd scope violations;
- `LIMIT_EXCEEDED` when no registry capacity is available or bounded limits are exceeded unexpectedly;
- `AUTHORITY_REQUIRED` / `AUTHORITY_EXPIRED` before the scoped process service is reached.

No error message should disclose another scope's process metadata.

## 17. Shutdown and failure behavior

Clean daemon shutdown attempts to stop all running managed processes before closing the transport.

Shutdown must be bounded. If children do not exit after graceful termination, the supervisor escalates to `SIGKILL` using the same process-group rules.

If the daemon crashes or is `SIGKILL`ed, detached managed processes can survive. The next daemon instance has no safe cryptographic ownership proof for those OS PIDs, so it does not discover or kill them automatically. This is a documented Phase-1 limitation.

No process registry or logs are persisted to disk.

## 18. Tests and acceptance

Automated tests must cover at minimum:

1. existing `terminal_run` behavior remains unchanged;
2. User/Project leases cannot start managed processes;
3. Admin can start an allowlisted `node` process with `shell:false` policy;
4. `sh` and executable paths remain denied;
5. cwd outside the authority scope is denied;
6. process IDs are opaque and OS PIDs are absent from MCP output;
7. status reflects natural exit;
8. logs collect stdout/stderr and truncate oldest bytes at the configured bound;
9. process list contains only manageable records;
10. unknown/unauthorized IDs both return `PROCESS_NOT_FOUND`;
11. stop is idempotent;
12. stop escalates from `SIGTERM` to `SIGKILL` for an uncooperative process;
13. registry limit never evicts a running record;
14. completed records are evicted oldest-first when capacity is needed;
15. one process started under an Admin lease remains manageable by a later compatible Admin lease after the original lease ends;
16. clean runtime shutdown terminates active managed children;
17. MCP catalog exposes all five process tools with strict schemas;
18. logs, process IDs, arguments, and lease IDs do not enter audit metadata;
19. Node 22, Node 24, and macOS-native CI remain green.

Manual Mac acceptance after automated CI:

1. locally authorize Admin with Touch ID;
2. `process_start` a harmless Node HTTP/dev fixture under `/Users/dogan/chatgpt-system`;
3. verify `process_status` is `running`;
4. verify `process_logs` returns fixture output;
5. verify the fixture is reachable locally if it opens a test port;
6. verify `process_stop` transitions it to `stopped`;
7. verify a second `process_stop` is harmless/idempotent;
8. verify a User lease cannot start or inspect the process;
9. verify `sh` remains `POLICY_DENIED`.

No acceptance step modifies user project files.

## 19. Security invariants

The implementation is not complete unless all of these remain true:

- no raw PID management surface;
- no arbitrary signal surface;
- no shell mode;
- no implicit privilege elevation;
- no process start without terminal-capable authority;
- no cwd escape from current authority roots;
- no command outside the active authority allowlist;
- no unbounded process count;
- no unbounded captured logs;
- no secret-rich environment inheritance;
- no process/lease/log secrets in audit metadata;
- no unsafe startup sweep of unrelated OS processes;
- no hidden process persistence promise across daemon restart.
