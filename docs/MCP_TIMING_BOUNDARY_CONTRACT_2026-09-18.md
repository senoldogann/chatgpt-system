# MCP timing boundary: source map and isolated verification contract (2026-09-18)

**Status: source-reviewed design only; not implemented or executed.** This document advances the user-approved, privacy-preserving isolated MCP timing study without retrying a previously safety-blocked timeout run or Git staging. It is not evidence of a live MCP performance gain.

## Correction: which transport is actually involved

- `src/cli.ts` branches on `command.mode`: `stdio` calls `startStdio(runtime)`; HTTP calls `startHttp(runtime)` separately. `src/transport.ts` defines `startStdio` using `serveStdio(() => createMcpServer(runtime), ...)` and `startHttp` using `createHttpServer`, a stateless MCP SDK handler and a separate HTTP bearer token. The ChatGPT tunnel/daily-driver path described in `docs/PROJECT_STATE.md` uses an MCP child with `dist/cli.js ... stdio`, not the standalone HTTP listener.
- Consequently, the independent localhost HTTP SDK prototype measures **only its own HTTP path**. Its client RTT, HTTP response `finish` and handler duration cannot be relabeled as hosted ChatGPT-to-local-MCP latency, or as the deployed stdio transport's timing. Any future real-host measurement needs an explicit stdio-side observation point and separately available hosted client timestamps; do not infer these from HTTP numbers.
- `src/audit.ts` `AuditLogger.run` times the awaited service callback and then awaits `recordBestEffort` outside that stopwatch. Existing audit durations omit audit persistence; they also omit MCP serialization, stdio pipe transfer, hosted dispatch and model reasoning. `src/server.ts` registers tools through both local registration and `registerBrowserTools`, with `safeCall` representing logical tool failure via MCP `isError`, not necessarily HTTP 4xx/5xx.

## Exact scope of a future disposable timer

**HTTP control experiment (not live MCP).** Reuse the SDK's existing localhost Host/Origin and bearer checks and preserve route handling verbatim. Only after these checks, create *one closure per admitted request* with its monotonic start timestamp and fixed mode/fixture class. Measure Node response `finish` (server finished handing bytes to the writable stream), premature `close` (if not writableFinished), and handler errors separately; settle exactly once, detach listeners, cap in-memory storage, and record no headers, payloads, full paths, request IDs or body. HTTP 2xx is a transport outcome, not a logical tool-success indicator. No logging of rejected 401/403 requests as authenticated tools. Do not use the earlier prototype's mutable process-wide `enabled`, `sampling`, `bucket`, `currentDelayMs` to label overlapping requests; each call's fixture identifier/expected delay is held in a local closure in a *test-owned client*, while the server timer knows only its own request start/outcome. Never read the JSON-RPC body simply to obtain action labels.

**Actual stdio boundary: later, separate design/approval.** `startStdio` does not expose an HTTP request/response object. First inspect the installed SDK for a supported, content-free message lifecycle hook and identify what timestamp is actually available. If no such supported hook exists, classify stdio roundtrip as **NOT_MEASURED**; do not wrap/parse raw stdio bytes, print metrics on protocol stdout, or conflate the audit `run` time with request RTT. If ever separately approved for production, all instrumentation must be opt-in, bounded, request-scoped, on a non-protocol output path, and subject to the full repository gate and a user-authorized runtime rollout. Hosted model generation and hosted request dispatch remain **NOT_MEASURED** unless the platform explicitly exposes them.

**Tool execution and cancellation.** Distinguish transport completion, tool `isError`, client-side abort, client-side timeout, and server callback completion. An SDK `AbortSignal` rejection must not be presented as rollback: in two previous successful disposable tests the server could still finish its operation and HTTP response after the client rejected. Server `res.finish` is not proof the client received or accepted a response. No server/client median subtraction to estimate a network component: trials must be paired and timestamp boundaries defined before making any derived timing claim.

## Test-first acceptance matrix (proposed, NOT RUN)

| Case | Pass criterion | Failure/reporting rule |
| --- | --- | --- |
| Two overlapping, intentionally inverted-duration requests | Each request-local timer generates exactly one terminal observation; each test-owned client duration stays assigned to its own fixture; no global label switch can contaminate samples. | Reject timing design if cross-attribution, missing records or duplicate settling occurs. |
| Bursts at 1, 2, 8 and 16 concurrent synthetic requests | Aggregate counts reconcile with admitted requests; finite bounded storage and no raw content. | Report observed scheduling variance, not causal speedup. |
| Unauthorized Bearer and hostile Origin | Existing 401/403 and no entry in authenticated request timing population. | Any bypass or leaked header fails. |
| Logical tool failure over HTTP 2xx | `isError` and HTTP status class represented separately. | Never report a 2xx tool result as unequivocal success. |
| Client `AbortController` and SDK timeout | Immediate client rejection is captured, and server work/response completion observed independently; both promises have rejection handlers attached before awaiting any other event. | A client cancellation does not imply server cancellation; failed or blocked cases remain UNVERIFIED. |
| Server error, premature close and repeated `finish`/`close` | Terminal measurement settles once, handles missing `finish`, and reports proper lifecycle class. | No fabricated successful RTT on failed response. |
| Canary payload, credential-like token, synthetic URL and target | Only aggregate timing/outcome class is emitted; fixture secrets absent from output and persistent audit. Request body untouched by timer. | Reject if substring/canary found, or if content is serialized. |
| Baseline vs timer (ABBA; 0 and 12ms separate strata, independent runs) | Per-stratum medians, p95, sample sizes, end-to-end client duration and timed server boundary reported with full provenance; correctness unchanged. | Small/inconsistent deltas cannot be claimed as acceleration or zero overhead. |
| Shutdown and cleanup | Test-owned listener/client and disposable files are verified closed/removed after successful authorized testing. | No completion claim without fresh cleanup evidence. |

## Prior evidence versus unverified work

- Prior *independent, disposable localhost HTTP* prototype had two stratified, successful 192-call runs (384 calls combined), plus earlier independent runs; the 0ms and 12ms strata showed millisecond-scale local SDK client RTT and no stable timer-on advantage. Authentication/origin, error-as-HTTP-2xx, privacy canaries and client-abort observations passed in those completed runs. Those calls were sequential and **do not** validate concurrency correctness.
- A later timeout variation initially exited nonzero from an early unhandled rejected promise. A local scratch-file change attached handlers earlier, but its verification invocation was **blocked by platform controls**. Do not report the variation as passing; do not repeat the blocked execution via another command, host tool or runner. Previous `git_stage_paths` was also platform-blocked. The existing partially staged Browser timing report/`PROJECT_STATE.md` and untracked scratch script remain intact, and no new commit should be claimed.
- A bounded local connectivity diagnosis around the user-provided 00:46 incident window reported a running stable runtime, 33 forwarded commands, zero tunnel warnings/errors/stdio failures. This does not identify or lift the platform security rejection.
